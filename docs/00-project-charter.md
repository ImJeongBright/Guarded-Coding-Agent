# Project Charter

## 1. 문제

코딩 에이전트를 실제 개발에 사용하면 코드 탐색, 파일 수정, 테스트 실행, Git 작업까지 위임할 수 있다. 위임 범위가 넓어질수록 사람이 반복적으로 확인해야 하는 작업은 줄지만, 모델의 잘못된 판단이 실제 side effect로 이어질 가능성도 커진다.

프롬프트나 Skill에 "하지 마"라고 적는 방식은 모델의 행동 확률을 바꾸는 soft constraint다. 이 프로젝트는 중요한 실행 경계를 모델의 순응 여부가 아니라 프로그램의 deterministic policy로 강제한다.

## 2. 프로젝트 목표

Guarded Coding Agent는 다음 사용 경험을 목표로 한다.

~~~text
사용자 작업 요청
    ↓
Coding Agent
    ↓
Tool Call 제안
    ↓
Policy Gateway
    ├─ ALLOW
    ├─ REQUIRE_APPROVAL
    └─ DENY
    ↓
실제 Filesystem / Shell / Git
    ↓
Validation + Audit
~~~

사용자는 정상적이고 되돌리기 쉬운 개발 작업은 자동화하고, 외부 영향이 크거나 비가역적인 작업만 직접 승인한다.

## 3. 사용자 문제

- 모든 tool call을 직접 확인하면 agent 자동화의 이점이 줄어든다.
- 모든 권한을 허용하면 실수의 영향 범위가 커진다.
- 프롬프트 금지사항만으로 실제 side effect를 보장하기 어렵다.
- 승인한 명령과 실제 실행된 명령이 다르면 승인 자체가 무의미하다.
- 정책이 너무 엄격하면 정상적인 개발 작업이 막혀 사용하지 않게 된다.

## 4. 목표

### G1. 실행 권한 분리

Agent의 제안과 실제 실행을 분리한다.

### G2. 최소 권한

필요한 tool과 범위만 제공한다.

### G3. 위험 기반 승인

정상 작업은 자동 허용하고, 높은 위험도는 승인 또는 차단한다.

### G4. 결정적 정책

중요한 정책은 LLM 판단이 아니라 코드와 구성으로 결정한다.

### G5. 감사 가능성

누가 무엇을 요청했고 어떤 규칙 때문에 허용·승인·차단됐는지 기록한다.

### G6. 실제 사용 가능성

보안 데모가 아니라 본인의 실제 개발에서 계속 사용할 수 있어야 한다.

## 5. 비목표

MVP에서 다음을 목표로 하지 않는다.

- 모든 종류의 AI agent framework
- 모든 shell command의 완전한 의미 분석
- production 보안 솔루션 인증
- 악성 운영체제 사용자에 대한 방어
- 컨테이너/VM 수준의 완전한 격리
- 여러 agent를 조정하는 multi-agent orchestration
- 모델 품질 자체 향상
- 기업용 IAM 또는 Zero Trust 플랫폼

## 6. 프로젝트 성공의 의미

이 프로젝트의 성공은 "모든 위험을 막았다"가 아니다.

다음이 가능하면 성공으로 본다.

- 정상적인 로컬 개발 작업을 실제로 수행할 수 있다.
- 명시한 위험 경계는 테스트로 재현 가능하게 강제된다.
- 승인 대상과 실제 실행 대상이 일치한다.
- 정책 우회 시나리오가 회귀 테스트에 누적된다.
- 본인이 실제 개발에 사용하면서 정책을 조정한 기록이 남는다.

## 7. 핵심 철학

> LLM interprets intent; the program enforces authority.

모델은 작업 의미와 필요한 행동을 제안한다. 프로그램은 실제 권한, 범위, 승인 여부와 실행 가능성을 결정한다.
