## R001 — diff가 읽는 과거 경로를 먼저 검증

기존 검사는 index의 `ls-files`만 확인했다. `.env`를 index에서 삭제하면 경로가 검사에서 빠졌지만,
`git diff --cached`는 HEAD의 삭제 전 blob을 읽어 반환할 수 있었다.

diff 본문 실행 전에 `--name-only -z`로 실제 변경 source 경로 전체를 수집하고 Filesystem 정책으로 검증한다.
metadata 조회와 본문 모두 `--no-renames`를 사용하므로 rename의 이전 경로도 삭제 source로 검사된다.
호출자가 새 파일 하나를 filter로 지정해도 전체 source 검사를 통과해야 한다.
정규화된 action에 `source_paths`를 포함하여 실행 직전 재검사에서도 변경 source가 같은지 확인한다.

NUL 종료, canonical 경로, 해석 가능한 파일명과 출력 한도를 검증한다.
조회가 잘렸거나 malformed이면 `GT-STATE`로 닫고 본문 executor를 호출하지 않는다.
가짜 `.env`의 staged 삭제·rename·새 이름 filter 우회가 거부되는지와,
unborn HEAD 및 일반 파일의 staged/unstaged diff가 계속 동작하는지를 회귀로 확인한다.

**호환성:** rename 표시는 삭제+추가 형태가 된다. diff filter에 포함되지 않은 민감 source도 거부한다.
민감 경로 보호를 유지하기 위한 범위 제한이며, 일반 파일의 삭제·변경 검토는 허용한다.

## R002 — 변경 후 실패를 미실행으로 기록하지 않음

기존 Gateway는 adapter가 정상 반환하지 않으면 초기 `executed:false`를 유지했다.
edit의 replace 후 directory fsync 실패나 write의 truncate 후 실패도 `DENY / 미실행`처럼 보였다.

Filesystem executor가 실제 효과 경계에서 생성·truncate·write·replace·unlink 상태를 기록한다.
변경 후 실패는 `ExecutionFailure`로 실행 여부, 효과 상태와 실패 단계를 전달한다.
Gateway는 실행을 시작한 오류에서 원래 정책 결정과 `matched_rule`을 유지하고,
별도 `execution_status`, `execution_stage`, `execution_error_rule`, `execution_error`를 반환·audit한다.

`effect_status`는 `none / partial / applied / possible`이다.
예를 들어 replace는 완료했지만 directory fsync가 실패하면 `executed:true / applied / failed`로 표시한다.
이는 내구성이 확인됐다는 의미가 아니다. command 실행은 내부 효과를 전부 관찰할 수 없으므로 보수적으로 `possible`을 사용한다.
실행 전 거부는 계속 `DENY / not_started / none`이다.
MCP는 정책이 ALLOW여도 실행 상태가 failed이면 `isError:true`를 반환한다.

회귀는 변경 전 truncate 실패, parent/new file 생성 후 실패, write 중단, replace 후 fsync 실패,
실패한 임시 파일 정리, nonzero command exit, 응답과 audit 일치를 구분한다.

**호환성:** `decision == ALLOW`만으로 성공을 판단하면 안 된다.
호출자는 실행 상태와 exit code, 효과 상태를 함께 확인해야 한다.
write는 계속 atomic replacement가 아니며, edit의 최종 검사와 rename 사이에 외부 writer를 막는 OS CAS를 추가한 것은 아니다.

## R003 — process group을 벗어난 자식까지 종료 확인

기존 `killpg`는 `start_new_session`, `posix_spawn`의 새 group, double fork 뒤 reparent된 자식을 놓쳤다.
tool 반환이나 timeout 이후에도 같은 write capability가 남을 수 있었다.

새 backend는 실행별 두 metadata marker를 `/private/tmp`의 별도 directory에 만들고,
Seatbelt policy에 하나는 허용·하나는 거부하는 identity를 넣는다.
marker는 command의 workspace/write scope와 겹치지 않으며 agent가 수정할 수 없다.
자식이 group·session·부모를 바꾸더라도 상속한 policy identity로 찾는다.

Darwin native API로 같은 UID의 process를 열거하고, PID와 pidversion을 확인한다.
signal은 `proc_signal_with_audittoken`을 사용해 kernel이 PID+version을 원자적으로 확인하게 한다.
검사와 signal 사이 PID 재사용이 다른 process를 죽이는 경로를 피한다.
보이는 scope member를 STOP 후 KILL하고 다시 검사하며, 완전한 빈 scan이 연속 두 번 확인돼야 cleanup을 완료한다.

process가 exec하는 동안 identity가 바뀌면 `_LifecycleRace`로 처리한다.
이는 member 없음이 아니라 **판단 불가**다. bounded 재검사 후에도 안정된 complete scan을 얻지 못하면 실패한다.
trusted startup self-test의 STOP/CONT 중 `sandbox-exec → sleep` exec가 경합하는 경우도 bounded retry한다.

backend/구조체 layout/열거 접근은 constructor에서 확인한다.
work 전에 native membership·signal과 최초 Seatbelt 이후 재초기화/bytecode apply가 거부되는지 self-test한다.
검사 불가이면 작업을 시작하지 않는다. 시작 후 cleanup이 실패하면 `SH-LIFECYCLE`, `executed:true`,
`effect_status:possible`로 보존하고 동일 Gateway의 후속 작업을 차단한다.
marker와 `scope.json`을 진단용으로 유지하며 operator recovery를 거친 뒤에만 재시작해야 한다.

untrusted command의 stderr에 `sandbox_apply: Operation not permitted` 같은 문구가 있는지만 보고
미실행으로 바꾸던 판단도 제거했다. 실제 command가 쓴 파일과 실행 상태가 보존되는지 회귀로 확인한다.
host capture에서는 이미 reap된 leader의 process group에 signal을 보내지 않는다.
그 번호가 재사용됐을 때 다른 group을 죽이지 않도록, unreaped 상태에만 group 종료를 수행한다.

회귀는 정상 반환·timeout의 detached child, posix_spawn 새 group, reparent된 grandchild,
일반 자식 실행, marker 접근 거부, backend/cleanup 실패, pidversion 불일치,
exec 경합과 reap된 host group을 구분한다.

**호환성:** macOS 15.7.8 arm64에서 확인한 native API와 ABI를 사용한다.
다른 OS·macOS 버전에 대한 검증은 없다. 검사 불가에서 제한을 풀어 실행하는 fallback은 없다.
완전한 CPU/memory quota나 악의적인 동일 UID operator·kernel 격리까지 보장하는 기능은 아니다.
OS 서비스에 요청해 대신 생성한 프로세스는 직접 상속 계보에 포함되지 않는다.
Guard controller 자체가 강제 종료되거나 crash한 경우의 자동 복구·잔여 프로세스 정리도 이번 검증 범위 밖이다.

## R004 — explicit file과 Git pathspec 의미를 일치

기존 `paths:["*.txt"]`는 한 문자열을 경로로 검사한 뒤 Git에서 wildcard로 확장되어 여러 파일을 stage했다.
옵션 구분자 `--`만으로는 pathspec 의미를 없앨 수 없었다.

모든 Git argv에 `--literal-pathspecs`를 적용한다.
add/diff의 filter는 실제 ordinary file 또는 index/변경 source에 있는 정확한 파일명이어야 한다.
directory·`.`·삭제된 directory prefix의 재귀 지정은 거부한다.
삭제된 일반 tracked file은 staging 및 staged diff를 계속 허용한다.
경로 metadata는 NUL 형식 그대로 처리해 Unicode와 앞뒤 공백을 보존한다.

회귀에는 없는 wildcard target의 무변경 거부, 실제 `*.txt`·`:(glob)*.txt` 파일명의 한 파일 staging,
directory 재귀 거부, 일반 삭제 파일, 공백·Unicode 이름과 malformed metadata를 넣었다.

**호환성:** glob/magic과 directory 전체 staging은 지원하지 않는다.
Agent는 search/list로 찾은 explicit 파일명을 지정한다. 특수 문자가 실제 파일명인 경우 literal 대상으로 허용한다.

## R005 — 해당 세션의 완료를 증거에 연결

기존 검증기는 현재 코드가 통과하고 누적 commit이 있으면 빈/실패 세션도 합격시켰다.
002는 CLI exit code도 확인하지 않았다.

launcher가 model 실행 전에 `session-baseline.json`을 만든다.
여기에는 full starting HEAD, clean 상태, workspace identity, policy digest, audit prefix의 byte cursor/hash를 기록한다.
종료 뒤 `session-completion.json`에 ending HEAD·새 reachable commits·변경 경로,
baseline binding, events/exit hash와 audit stop cursor를 기록한다.
현재 collector는 검증 가능한 attribution을 위해 clean checkout와 기존 HEAD를 요구한다.
이는 Gateway의 Filesystem/Shell/Git 정책에 추가한 제약은 아니다.

002·003은 CLI 0과 성공한 model turn 외에 실제 Guard filesystem mutation, 성공한 shell 검사,
explicit staging, local commit을 요구한다.
각 call의 audit ID·run/actor·policy·canonical action·execution 결과를 session audit window와 비교한다.
이전 audit를 재사용하거나, call 없이 audit action만 있거나, 새 commit이 성공한 Guard commit 응답에 귀속되지 않으면 실패한다.
starting HEAD가 ending HEAD의 ancestor여야 하며 새 commit과 실제 파일 변경이 있어야 한다.

과거 add/deletion/staged diff를 종료 시점의 index로 다시 normalize하지 않는다.
당시 audit의 source set과 caller-controlled args를 비교하므로 정상 삭제 commit도 검증할 수 있다.
Codex가 MCP `isError` 때문에 `status:failed`로 표시한 red test는 transport 실패와 구분한다.
정상 audit와 nonzero test 결과가 있고 이후 수정·성공 검사가 있으면 개발 반복으로 허용한다.
transport error 또는 결과 누락은 거부한다.
독립 behavior 검사와 clean ending status는 계속 별도 조건으로 유지한다.

회귀는 빈 세션, CLI/transport/turn 실패, 이전 commit·call 재사용, 증거 누락·변조,
argument/audit 불일치, dirty start와 정상 write/check/add/commit을 검증한다.
실제 Guard에서 002 Python 독립 계약의 성공·실패도 확인했다.

**호환성:** 이 검증기는 edit/check/stage/commit을 요구하는 002·003 workload의 완료 판정기다.
read-only/no-op task를 판정하는 일반 도구가 아니다.
새 baseline/completion이 없는 기존 002·003 로그는 당시의 역사적 실행 결과로 보존하지만,
새 규칙으로 소급 재인증하지 않는다. 부족한 시작 증거를 사후 추정해 합격시키지 않는다.

## R006·R007 — 부분 검색 결과와 생략 상태를 정확히 반환

R006에서는 entry 열거 상한을 넘은 flag가 이미 모은 파일의 처리까지 중단했다.
열거 중단과 처리/출력 중단을 분리해, 모은 파일은 기존 byte/result 한도 안에서 검색한다.
상한 5,000 entries·8 MB 읽기·200 matches·64 KB 출력은 유지한다.
파일이 검사 뒤 커져도 남은 byte budget보다 더 읽지 않도록 read bound도 전달한다.

R007에서는 대형 파일과 잘린 list를 완전한 결과처럼 반환했다.
직접 지정한 대형 파일의 text search는 `FS-SIZE`로 거부한다.
재귀 탐색에서 큰 파일을 건너뛰면 `file_size_limit`과 `skipped_oversized_files`를 반환한다.
list/search에 `truncated`, `incomplete`, `truncation_reasons`를 넣는다.
list는 열거 5,000개·반환 2,000개·UTF-8 64 KB로 제한하고 scanned/returned entries를 구분한다.

회귀는 5,001개 검색 파일에서 부분 match가 남는지, 직접/재귀 대형 파일,
읽는 중 파일 성장, list entry/result/output 상한, Unicode byte 계산과 완전한 소규모 결과를 확인한다.

**호환성:** 반환 field가 추가된다. `matches:[]`만으로 일치하는 파일이 없다고 결론내리면 안 된다.
`incomplete`와 생략 이유를 확인하고 경로·glob을 좁혀 재요청할 수 있다.
민감/protected/link 및 binary/non-UTF-8 제외는 기존 탐색 계약을 유지한다.

## 시행착오와 확인한 실행 기록

R003을 단순 syscall 차단으로 해결하는 경로도 실제로 시험했다.
`setsid/setpgid` 계열만 막아도 posix_spawn의 group 분리는 남았고,
posix_spawn syscall 244까지 막으면 Python launcher·compiler·Node의 정상 자식 실행이 깨졌다.
`__mac_syscall`을 통째로 차단하는 방식도 dyld/ld의 정상 권한 query를 깨뜨렸다.
그래서 command spawning을 유지하면서 inherited policy identity로 종료를 확인하는 backend를 채택했다.

첫 전체 실행은 **156개 / failures 13 / errors 7 / skips 0 / 26.867초**로 실패했다.
여러 오류의 공통 원인은 trusted startup/exec 중 identity 변경을 즉시 backend 실패로 본 race 처리였다.
미확정 scan을 `_LifecycleRace`로 보존하고 startup retry를 추가한 뒤 다시 검사했다.
최종 [회귀 JSON](evidence/fix-001-003/regression-final.json)은 **159개 / failures 0 / errors 0 / skips 0 / 34.666초**다.
macOS 15.7.8 arm64 / Python 3.12.1, 2026-10-04T14:39:34Z 기록이다.
최초 실패는 [별도 JSON](evidence/fix-001-003/regression-first-156-failed.json)으로 그대로 보존했다.

## 수정 후 runtime 비용과 사용성

[실 C 세션의 timings](evidence/fix-001-003/live-c/timings.json)은 ALLOW 호출의
반환된 `total - execution`을 Guard boundary 비용으로 집계했다.
normalization 재검사, schema/hash 및 audit는 포함하고, model 추론과 MCP transport는 포함하지 않는다.
Git의 state-query subprocess는 normalization에 포함된다.

| Tool | ALLOW 표본 | Boundary median | Boundary p95 | Execution median |
|---|---:|---:|---:|---:|
| Filesystem | 8 | 1.038 ms | 1.707 ms | 0.502 ms |
| Shell | 2 | 4.223 ms | 4.404 ms | 449.851 ms |
| Git | 6 | 104.454 ms | 197.799 ms | 46.598 ms |

Shell의 execution에는 실제 command뿐 아니라 native lifecycle setup/self-test/cleanup이 포함된다.
Git은 실행 전 source/index 검사를 위해 여러 query를 수행하므로 boundary 비용이 더 크다.
전체 regression 시간이나 작은 표본의 p95를 Guard on/off 성능 비율로 해석하지 않는다.

이번 정상 개발 task에서는 policy 재등록·외부 승인 없이 source 수정, build/test, diff, explicit staging과 commit을 완료했다.
합성 X의 정상 25개에서도 approval/denial은 없었다.
따라서 **검증한 ordinary local repository와 전용 host 구성에서는 지속 사용을 막는 문제가 재현되지 않았다.**
잘못된 프롬프트가 만든 denial 1회와 setup/host 제한은 그대로 남기며,
dependency installation, linked worktree, symlink-heavy 프로젝트나 장기간 실제 사용자 경험의 판정으로 확대하지 않는다.

전체 재검증은 macOS Seatbelt 실행이 가능한 host에서 수행한다.

## 증거 보존과 판정의 범위

raw 증거는 `.guard-runs/fix-001-003/`에 보존한다.
최종 [portable evidence](evidence/fix-001-003/README.md)에는 수정 source manifest, 회귀, call/audit, baseline/completion,
정책, 독립 check, patch와 copied baseline/final source를 함께 보존한다.
host auth·host logs/SQLite·승인 DB는 export하지 않는다.

개인 경로 치환이나 content redaction은 원래 events/audit의 byte hash·cursor를 바꾼다.
portable 복사본은 원래 검증 결과를 보여주는 변환본임을 명시하고,
raw 검증 binding과 변환본 hash를 구분한다. 변환 후 새 hash를 만들어 원래의 시작 캡처처럼 주장하지 않는다.

수정 전 003의 latency 수치는 수정 후 lifecycle 검사의 성능을 입증하지 않는다.
추가된 native 검사 비용과 현재 개발 흐름의 denial/approval 수는 위의 새 세션 수치로 구분한다.
macOS/Codex의 제한된 local workload 결과를 다른 host·OS, dependency installation,
대규모 저장소나 실제 사용자의 장기 만족도로 확대하지 않는다.
