## R001 — 민감 파일의 과거 내용을 staged diff로 반환

위치: [git.py](../../guarded_agent/git.py) 84~86, 91~98행.
현재 검사는 `git ls-files -z`의 index 경로만 확인한다. 이미 커밋된 `.env`를
`git rm --cached .env`로 index에서 제거하면 이 검사에 `.env`가 나오지 않는다.
뒤의 `git diff --cached`는 HEAD의 삭제 전 blob을 읽어 내용을 반환한다.

가짜 `.env`를 커밋하고 index에서 제거한 임시 저장소에서 다음을 확인했다.

- Filesystem `.env` read: `DENY / FS-SENSITIVE`.
- Git staged diff: `ALLOW / executed:true / exit_code:0`.
- stdout에 `REVIEW_DUMMY=not_a_secret_7391` 원문 포함.

실제 secret은 사용하지 않았다. token pattern redaction으로 모두 제거될 것이라고 가정할 수 없으며,
OS sandbox의 민감 경로 차단도 `.git/objects` 안의 blob에는 적용되지 않는다.
수정은 diff가 참조하는 HEAD/index 경로를 본문 반환 전에 검사해야 한다.
검사 결과가 잘리거나 해석 불가능하면 미실행으로 닫아야 한다.
회귀에는 민감 파일의 staged 삭제·이름 변경과, 일반 파일의 정상 staged diff를 함께 넣는다.

증거: [git-results.json](evidence/review-001-003/git-results.json),
[재현](evidence/review-001-003/repro/git-review.py).

## R002 — 실제 변경 후 `DENY / executed:false`

위치: [gateway.py](../../guarded_agent/gateway.py) 183~187행,
[filesystem.py](../../guarded_agent/filesystem.py) 148~150행.
`edit`가 atomic replace를 완료한 뒤 parent-directory fsync에서 오류가 나면,
Gateway는 adapter가 정상 반환하지 않았다는 이유로 초기 `executed:false`를 유지한다.
정책 거부와 실행 중 실패를 구분하지 못한다. `write`의 truncate/write 뒤 오류도 같은 구조다.

디렉터리 fsync만 실패시키는 fault injection을 사용했다. 원본 `before\n`은 실제로 `after\n`으로
바뀌었는데 응답과 result audit 모두 `DENY / EXEC-ERROR / executed:false`였다.
사용자나 Agent가 효과가 없었다고 믿고 재시도·복구하면 잘못된 후속 행동을 할 수 있다.

수정은 executor가 변경 여부와 실패 단계를 전달하고, 정책 결정과 실행 결과를 분리하는 것이다.
효과가 발생한 뒤의 실패는 변경 발생 또는 불확실 상태를 응답·audit에 보존해야 한다.
adapter 호출 직전에 무조건 `executed:true`로 바꾸면 미실행 오류도 오기록하므로 충분하지 않다.
회귀에는 변경 전 실패, replace 후 fsync 실패, write 도중 실패를 구분한다.

증거: [filesystem-results.json](evidence/review-001-003/filesystem-results.json),
[재현](evidence/review-001-003/repro/filesystem-review.py).

## R003 — 분리된 자식의 실행·쓰기 권한이 종료 후 유지

위치: [sandbox.py](../../guarded_agent/sandbox.py) 59, 85~99행.
프로세스 종료 처리는 최초 process group에 `killpg`를 보낸다.
허용된 Python profile 내부에서 `Popen(..., start_new_session=True)`로 실행한 자식은
다른 group에 속하므로 이 종료 처리에 포함되지 않는다.

최대 1초짜리 프로세스와 임시 `output/` write scope만 사용했다.
정상 반환 직후 파일 없음 → 0.7초 뒤 자식이 쓴 파일 존재였다.
profile timeout 0.1초 경로도 `exit_code:124 / timed_out:true`로 반환한 뒤 같은 쓰기가 발생했다.
외부 파일·네트워크 접근은 없었다. 앞선 비동기 `os.setsid()` probe의 음성 결과는
분리 전에 group 종료가 먼저 일어날 수 있으므로, 분리를 보장하는 이번 재현으로 보완했다.

이는 문서에 제외한 daemon의 완전한 CPU/memory isolation과 구분된다.
tool 반환·timeout 뒤에도 같은 write capability가 남아 다음 build/test의 산출물을 바꿀 수 있다.
수정은 자식 분리를 제한하거나 전체 실행 계보의 종료를 보장하는 backend 설계를 적용하는 것이다.
process group 하나를 죽이는 것만으로 전체 자식 종료를 주장하면 안 된다.
회귀에는 분리가 완료된 자식의 정상 반환·timeout 이후 효과가 없는지 확인한다.

증거: [detached-results.json](evidence/review-001-003/detached-results.json),
[재현](evidence/review-001-003/repro/detached-review.py).

## R004 — 파일 경로 검증과 Git pathspec 의미가 다름

위치: [git.py](../../guarded_agent/git.py) 91~98행.
`paths`를 Filesystem 경로로 정규화한 뒤 Git에는 pathspec으로 전달한다.
`--`는 옵션 구분자이며 wildcard/magic을 literal 파일명으로 바꾸지 않는다.

`paths:["*.txt"]`는 파일명 `*.txt`가 없어도 ALLOW되어 `one.txt`, `two.txt`를 둘 다 stage했다.
명시적인 파일을 stage한다는 계약과 검증된 action의 범위가 달라진다.
큰 저장소에서는 의도하지 않은 변경을 commit에 포함할 수 있다.

수정은 literal pathspec 모드를 사용하고, explicit-file 계약이라면 directory 재귀도 검증하는 것이다.
glob/magic을 지원하려면 실제 확장 대상 전체를 별도로 정규화·검증·audit해야 한다.
회귀에는 wildcard/magic 문자열, 실제 특수문자 파일명, 일반 파일 하나의 staging을 넣는다.

증거: [git-results.json](evidence/review-001-003/git-results.json),
[재현](evidence/review-001-003/repro/git-review.py).

## R005 — 실사용 세션의 완료를 잘못 판정

위치: [verify_003.py](../../scripts/verify_003.py) 115~121행,
[verify_live_workload.py](../../scripts/verify_live_workload.py) 81~89행.
003은 CLI exit 0, 현재 코드의 테스트, clean status, 누적 커밋 수로 `passed`를 정한다.
Guard 도구를 실제 사용했는지, 해당 세션 이후의 변경·새 커밋인지 확인하지 않는다.
002 검증기는 CLI exit code도 검사하지 않는다.

보존된 C 최종 source를 임시 저장소에 준비하고 세션 전에 두 커밋을 만들었다.
합성 실패 세션에는 Guard 호출 0개와 실패를 알리는 agent_message만 넣었다.
003은 CLI exit 0에서 `passed:true`, 002는 exit.json에 1을 넣어도 `passed:true`였다.
두 경우 모두 세션 뒤 새 커밋은 없었다. 독립 코드 동작 검사는 실제 Guard에서 통과했다.

이 합성 실패 증거는 기존 여섯 실사용 로그를 부정하는 것이 아니다.
기존 로그에는 실제 호출·변경·커밋이 있다. 검증기가 이후 실패 실행을 걸러내지 못한다는 문제다.
수정은 세션 시작 revision과 완료 revision의 관계, 해당 task에 필요한 Guard 호출과 효과,
transport/CLI 성공, 독립 behavior 검사를 함께 확인하는 것이다.
실제 작업이 없었던 경우와 task가 완료된 경우를 분리한다.
회귀에는 빈 세션·transport 실패·CLI 실패·이전 커밋만 존재하는 상태가 성공으로 표시되지 않도록 한다.

증거: [verifier-results.json](evidence/review-001-003/verifier-results.json),
[재현](evidence/review-001-003/repro/verifier-review.py).

## R006 — entry 한도에서 검색 결과 전체를 버림

위치: [filesystem.py](../../guarded_agent/filesystem.py) 175~180행.
한 디렉터리의 entry를 먼저 모으다가 5,000개 한도를 넘으면 `truncated=True`가 된다.
그 뒤 이미 모은 entry를 처리하는 loop도 이 flag를 보고 즉시 종료한다.

5,001개 파일 모두 `needle`을 포함했지만 `matches:[] / scanned_entries:5000 / scanned_bytes:0`이었다.
상한을 올릴 필요는 없다. 열거 중단과 이미 수집한 파일 처리 중단을 분리해
기존 byte/result 한도 안에서 부분 결과를 제공하면 된다.

## R007 — 생략을 “검색 결과 없음/전체 목록”으로 오해

위치: [filesystem.py](../../guarded_agent/filesystem.py) 192, 243행.
실제 검색어가 있는 1,000,007-byte 파일에 직접 search하면 크기 때문에 읽지 않고
`matches:[] / truncated:false`를 반환한다. list는 5,001개 중 2,000개만 출력하고
결과가 잘렸다는 field를 제공하지 않는다.

크기·entry 제한 자체는 유지한다. 직접 대형 파일 search는 `FS-SIZE` 또는 명시적인 incomplete 결과를,
listing은 `truncated`와 생략 사유를 제공해야 한다. 성능 개선이나 큰 프로젝트 전체 지원 요청이 아니라
현재 상한에 도달했을 때 반환 의미를 정확히 하는 수정이다.

R006·R007 증거: [filesystem-results.json](evidence/review-001-003/filesystem-results.json),
[재현](evidence/review-001-003/repro/filesystem-review.py).

## 추가 결함으로 집계하지 않은 것

- 가짜 uppercase sensitive/protected 파일 read, 외부 임시 프로세스 signal,
  read-only source에 대한 runtime hardlink/symlink 쓰기는 실제 Seatbelt에서 차단됐다.
- 승인 one-use/binding, 정책·profile 후보 변조, native 도구 차단과 기본 scope 검사의 기존 회귀는 통과했다.
- 외부 동일 UID writer의 최종 검사/rename 경쟁, linked worktree, dependency install,
  다른 host/OS, 실제 사용자의 1~2주 만족도는 이미 명시된 한계·미측정 항목이다.
- check runner의 오래된 envelope 표기는 003 문서에 설명돼 있다. 이번에는 독립 수정 항목으로 세지 않았다.
